# Agreement Routes

RESXPECT supports different ways for an agreement to begin depending on who initiates the work relationship and whether the agreement is ready to be funded immediately.

Although the entry point may differ, accepted agreements ultimately enter the same protected agreement lifecycle.

## Core Routes

RESXPECT currently supports three primary agreement routes:

**Creator Funded**

**Creator Proposal**

**Runner Proposal**

Each route provides a different starting point while preserving the same underlying agreement structure.

---

## Creator Funded

A Creator can create an agreement, define the work and fund it before inviting a Runner.

Conceptually:

**Creator Creates Agreement → Funds Agreement → Shares / Assigns to Runner → Runner Accepts → Start Work**

This route is useful when the Creator already knows:

- What work is required
- The proposed agreement value
- The intended Runner

Funding the agreement before the Runner begins provides assurance that the agreed value has already been committed.

---

## Creator Proposal

A Creator may also create and send an agreement proposal before funding is completed.

Conceptually:

**Creator Creates Proposal → Shares with Runner → Runner Reviews → Agreement Accepted → Funding → Start Work**

This gives the Runner an opportunity to review the proposed terms before the agreement becomes active.

The agreement only proceeds into protected work once the required conditions for activation have been met.

---

## Runner Proposal

A Runner can propose an agreement to a Creator.

Conceptually:

**Runner Creates Proposal → Shares with Creator → Creator Reviews → Agreement Accepted → Funding → Start Work**

This allows someone offering work or a service to define the proposed scope and send it directly to the person expected to fund the agreement.

The Creator can review the proposal before deciding whether to proceed.

---

## Agreement Links

Agreement proposals may be shared using RESXPECT links.

A link provides the intended participant with access to the relevant agreement or proposal so they can review the terms and take the appropriate action.

Links are a delivery mechanism for an agreement rather than a separate agreement type.

For example:

**Runner Proposal → Share Link → Creator Reviews**

or:

**Creator Proposal → Share Link → Runner Reviews**

Once accepted and activated, the agreement continues through the normal RESXPECT lifecycle.

---

## One Protocol, Different Entry Points

The route used to create an agreement does not change the core protection model.

Once an agreement becomes active, it follows the same underlying structure:

**Funding → Start Work → Evidence → Review → Completion / Dispute**

This keeps the protocol consistent regardless of which participant initiated the agreement.

---

## Marketplace

RESXPECT may support additional discovery or marketplace-based agreement routes in the future.

Marketplace functionality is separate from the core direct agreement routes and is not required for two parties to create a protected agreement.

---

## Public Specification

This document describes the public agreement entry routes supported by RESXPECT.

Internal invitation tokens, private API routes, authentication logic, link security mechanisms and production routing implementation are not disclosed in this repository.
